Overview

MathDeck is a classroom card game: each player holds number and operator cards and builds an equation that reaches the target on the board. Underneath it is a server-authoritative rules engine, so the client sends only what the player intends to do, and the server decides what actually happened.

The design rests on one idea: handle(State, Command) → Event[] is a pure function, and State is a fold over the event log. That single decision gives determinism, server authority, built-in telemetry and table-driven tests, and it lets three browser apps (the game, a deck editor and a teacher dashboard) share one source of truth.

Architecture

Dependencies point inwards. The pure engine depends on nothing, and deptrac fails the build if that ever changes.

Key features

Play is decided on the server

Commands carry intent (PlayCards{cardIds}), never a score or a result, so a tampered client has nothing to forge. The browser shows a live preview of the equation, but it's clearly marked "preview; the server decides".

Arithmetic uses exact fractions throughout. With floating point, 1 ÷ 3 × 7 × 3 evaluates to 6.999999999999999, and a child who answered correctly would be told they were wrong.

Mistakes are recorded as teaching data

Each rejection carries a reason code designed for teaching, such as OFF_BY_ONE or OPERATOR_PRECEDENCE_IGNORED. The second one fires only when the learner's answer matches a left-to-right reading but not the correct one.

A worker projects the event log into the teacher dashboard: overall accuracy, where learners go wrong, how long attempts take (median and 90th percentile, measured on the server) and a per-learner table. Analytics stores pseudonyms, not names.

Decks are data, checked before they ship

Teachers write new decks (numbers, operations, targets, hand size) without any code change. Each deck is validated against a JSON Schema.

A valid deck can still be impossible to play, so publishing runs a solvability linter that searches for an expression reaching each target. An unreachable target blocks publishing. Published decks are frozen, and an edit forks a new version, so finished matches always replay exactly as they were played.

Engineering notes

Persistence without stored state

No game state is stored anywhere. A match is fully described by its seed record plus its event log, so there's no serialised state to version or migrate. The primary key on (match_id, seq) is the concurrency control: two writers racing for the same sequence number can't both succeed, and the loser reloads and decides again.

Retries are safe

Idempotency-Key is required on every command and is written in the same transaction as the events it produced. A retry over flaky school wifi returns the original events instead of playing the cards twice.

Hardening

  • HMAC-signed, expiring tokens with the role as a signed claim. Sign-in failures are indistinguishable, so the API can't reveal which children have accounts.
  • Mutation testing with Infection on the arithmetic, rules and analytics. It raised the mutation score from 76% to 90% and found a helper that was not only untested but wrong.
  • CI runs static analysis (PHPStan), architecture rules (deptrac), both test suites against real MySQL, the browser-client tests and mutation testing.
  • The external API contract is an OpenAPI 3.0 spec, and the Postman collection is generated from it rather than written by hand.
